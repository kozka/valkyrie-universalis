# Porting Valkyrie's C# to TypeScript

The goal is that someone who knows Valkyrie's code (Quantumrunner) finds the same thing in the same place, so a fix on one side can be repeated on the other without searching.

## Pinned source
- Valkyrie 3.28, commit `752d4206738f00a6d41e34be56fe7e65e7b35965` (master, 20 June 2026), cloned into `referencias/valkyrie`.
- When Valkyrie publishes a new version: run the battery against it, port the diff, and record the new commit in `referencias/clonar.mjs`, `referencias/README.md` and `docs/port-status.md`.

## Layout (npm workspaces)

| `unity/Assets/Scripts/Quest/*.cs` (game-agnostic parts) | `packages/engine/src/Quest/*.ts` |
| `libraries/ValkyrieTools/*.cs` | `packages/engine/src/ValkyrieTools/*.ts` |
| `libraries/FFGAppImport/**/*.cs` (only what the browser needs: whether an import is needed) | `packages/engine/src/FFGAppImport/**/*.ts` |
| `GameType.cs` (abstract class) | `packages/engine/src/GameType.ts` (interface) |
| `MoMGameType` and every MoM-only branch | `packages/module-mom/src/` |
| `D2EGameType` and every D2E-only branch | `packages/module-d2e/src/` |
| `unity/Assets/Scripts/UI/Screens/*.cs` | `packages/app/src/screens/<Name>.tsx`: the screen's logic ported (with the notice and reference comments), its drawing rewritten in React |
| `unity/Assets/Scripts/UI` widgets, `Quest/*Window.cs`, `*Canvas.cs` (their drawing) | `packages/app/src/` (React and PixiJS; rewritten, not ported) |
| `unity/Assets/Scripts/QuestEditor/*.cs` | `packages/engine/src/QuestEditor/`: what the editor does to a quest and its files (save, reload, package, new, copy, delete, rename, reorder, test), with `tests/QuestEditorTests.test.ts`; `packages/app/src/editor/`: its screens, rewritten in React |

| Base data copy (`StreamingAssets/content/**/*.ini|txt`, `StreamingAssets/text`, and the text files of `Resources` that game rules read, such as `slidepuzzles.txt`) | `packages/engine/data/`, written by `tools/sync-valkyrie-data.mjs`; `Resources.Load` of a text becomes `Resources.loadText` (`platform/Resources.ts`) |

A module's inner layout (manifest, schema, ui, i18n, import recipe) is in `docs/plan.md`, section «El módulo de un juego».

## Conventions
- Same file names and class names. Methods and fields keep Valkyrie's words in camelCase (`Populate` becomes `populate`). Nested classes such as `QuestData.Tile` become exported classes in the same file (`QuestData.ts` exports `Tile`).
- Every ported file starts with a notice, as Apache-2.0 §4(b) requires for modified files: `// Ported from Valkyrie (Apache-2.0), modified: Content/QuestData.cs`. Every ported function then gets a one-line reference: `// Valkyrie: QuestData.cs Quest.Populate`.
- Keep the order of operations, even when it looks odd. Valkyrie's variables are 32-bit floats: use `Math.fround` where C# would round. Parse numbers culture-invariantly.
- Game-type branches become `GameType` members or module hooks, with the reference comment. That covers the 77 type checks in 30 files and about 20 more lookups keyed by `TypeName()`; the grep and examples are in `docs/contexto-tecnico.md`.
- Valkyrie draws random numbers without a seed. The engine takes an injectable seeded generator, so tests and the battery are repeatable.
- The engine has no DOM: it runs in Node for tests and in a Worker or on the main thread in the app.

## C# to TypeScript
- **Files**: Valkyrie calls synchronous `System.IO` everywhere (`File.Exists` in `FindLocalisedMultimediaFile` and `EventManager.QueueEvent`, `ReadAllLines`, `Directory.GetFiles`). Load the whole package first, asynchronously, into an in-memory virtual file system. It answers synchronously, ignores letter case, accepts `\`, and resolves `..` and `//`. Ported code calls that file system where C# called `System.IO`.
- **`Application.Quit()`** on fatal paths (`Quest.cs` 1172, 1689 and 1702; `QuestData.cs` 167) becomes `Application.quit(reason, component, message)`. It records a typed `ValkyrieFatalError` in `Application.fatalErrors` and returns, because Unity also keeps running the code after `Quit()` until the frame ends (Valkyrie's own tests rely on that). The host checks `Application.fatalErrors` after each step and stops the scenario with a clear message; the battery counts it as `fatal`.
- **`Game.Get()`** stays a global accessor, as in C#, so ported code reads the same: the host sets `Game.game`. It is null in unit tests, as in Valkyrie's EditMode tests, so a test that reaches it fails the way the NUnit test does (`NullReferenceException` becomes a `TypeError`). Code that only needs the language and the game type takes an `IGameProvider`, as Valkyrie's does.
- **Unity calls inside game logic** (dialogs, board drawing, camera, audio): the engine keeps Valkyrie's classes with their state and rules (`DialogWindow`, `HeroCanvas`, `TokenBoard`, `Audio`…). Wherever Valkyrie draws, opens a window or destroys objects by tag, it calls `game.ui` (`GameUI.ts`), which the app implements and tests replace with `HeadlessUI`. Board objects keep the state Unity's would (`platform/GameObject.ts`: position, rotation, size, colour, picture) and go to `game.ui.boardCanvasAdd` or `tokenCanvasAdd`. An exception in drawing code that changes nothing is not reproduced; one that stops an event is, in the engine, except a missing monster or item picture whose size Valkyrie reads (`MonsterIcon`, `DrawMonster`, `InventoryWindow`, `InventoryWindowMoM`, `DialogWindow.DrawItem`, `ShopInterface`), which is logged since 16 October 2026 while the app draws a placeholder, so that one author mistake does not stop the scenario. The play windows' rules live in the engine's `Quest/`, as in Valkyrie's layout, MoM-only ones included (`MonsterDialogMoM`, `PuzzleCodeWindow`…). What Valkyrie decides when it draws a window (a greyed button, a label from `Event.GetButtons`, which can log) is fixed when the window opens, in `ReactUI` or the engine's `CreateWindow`, never recomputed in a React render. A button Valkyrie leaves live stays live, even when pressing it seems to do nothing: its handler may change something first (`HeroCanvas.EndSection` sets each chosen hero's variable before it checks there are enough, and scenarios read them). A Unity drag handler (`BlockSlider`, `IUpdateListener`) becomes engine methods that take the pointer's offset in Valkyrie's UI units and say where the piece goes and what a drop does (`PuzzleSlideWindow.dragPosition`, `PuzzleImageWindow.dragOffset`, `PuzzleTowerWindow.hover` and `release`), so its clamps and rounding are tested without a browser. The app only turns pixels into units, measured where the pointer goes down, moves and goes up (Unity's drop frame reads the pointer too), and answers as Unity's `GetMouseButton(0)` does: the left button or the first finger, with a cancelled touch ending as a release.
- **Pictures**: `ContentData.fileToTexture` reads the size from the file header (DDS, PVR, PNG, JPEG) and gives a `Texture2D` of that size, or null where Valkyrie does; the app decodes and draws the pixels (`board/pictures.ts`; an atlas part is `Texture2D.cutFrom`, whose rows count from the bottom). Stand-ins (`platform/StandInFile.ts`) must have the real size, because positions and atlas bounds depend on it: Valkyrie's own pictures take theirs from `manifest.json` and are fetched from its repository when drawn; without the official import (schematic mode) its tiles take theirs from `board/schematic-tiles.json` and the rest are 4096×4096, and the app draws a schematic.
- **Board**: the engine hands Unity's objects to `game.ui` (`boardCanvasAdd`, `tokenCanvasAdd`, `questUICanvasAdd`, `destroyObject`, `destroyTag`); `board/registry.ts` keeps them in sibling order, and `findTag` must see them (a highlight is tagged `dialog`, which makes `TokenControl.startEvent` ignore clicks). The board does each frame what `Game.Update` does (`currentQuest.update(deltaTime)`) and what `CameraController.FixedUpdate` and `Update` do (`board/camera.ts`). A click presses the control of the topmost piece under the pointer, tokens over tiles and quest UI elements over both, even when it is transparent, as Unity's raycast does. The camera only drags or zooms when every piece under the pointer is tagged `board` (`ScrollEnabled`), and a held drag is applied every frame, not only when the pointer moves. Positions are board units with y up: draw at (x, −y) with rotation −θ. Windows keep Valkyrie's tags (Descent's activation window is `activation`, not `dialog`). Valkyrie's windows do not block the rest of the screen, and Descent needs that: its heroes and monsters are pressed with a window open (a hero knocked out during a monster's activation, chosen for an event), so they sit above the window layer (`QuestScreen.css`).
- **Sound**: the engine says which file to play (`Audio.ts`); the app's `audio/player.ts` ports what `Audio.cs` does with it (music loop and fade, effects, volumes) and `audio/webAudio.ts` plays it with the Web Audio API, because iOS ignores a media element's own volume. iOS starts an `AudioContext` only on a touch that ends (`touchend`, `click`, `pointerup`), never on `pointerdown`, and leaves it `interrupted` after a call: resume it on those whenever it is not `running` (3 November 2026: an iPad played nothing). Safari before 26 cannot read Ogg Vorbis, the import's format: there `.ogg` files are decoded with WebAssembly (`audio/oggDecoder.ts`), loaded only by those browsers and left out of the service worker's list; `sound.spec.ts` makes Chromium say it cannot read Ogg to test it. Valkyrie's base sounds are all `{import}`: without the import only a scenario's own sounds play. The menus' own sound (`audio/menuAmbience.ts`, not in Valkyrie) is apart from that player and uses the same `AudioContext`; it times itself by the context's clock, so it waits while the page is hidden. A piece of music is fetched whole and played from a blob: a media element pointed at the file asks for a range, and the service worker cannot keep a 206 answer (`cache.put` throws). A test that counts the sounds played must leave out the buttons' click and the wind (`sound.spec.ts`). The music has two volumes (not in Valkyrie): Valkyrie's `music` is the official import's, and a scenario's or a pack's own has `customMusic` among the app's settings; `webAudio.ts` marks each clip `imported` and `player.ts` sets the volume when a piece starts (`setMusicVolumes` from the options), so never write `output.music.volume` from a screen. Volumes are 32-bit floats: a test compares values such as 0.25 or 0.5.
- **Saves**: `SaveManager` writes Valkyrie's layout (`save.ini`, `image.png`, the scenario in `quest/`) to `<game>/Save` in the virtual file system, which the app keeps in the browser. The picture comes from `game.ui.takeScreenshot`: a PNG of the board at 4/30 of its size, taken after the next frame as `WaitForEndOfFrame` does (`HeadlessUI` gives none). As in Valkyrie, the autosave comes at the end of each round, on a change of quest and on quitting, not when a quest starts. The zip is written on the page's thread, so it copies as they are stored the files still mounted from a package or a save (`ZipManager` remembers each mounted file's entry) and the entries an update leaves alone, as DotNetZip does: recompressing a TLE scenario (32 MB) stopped the page 3–4 s at every autosave.
- **Kept files**: the app keeps Valkyrie's user folder in the browser (`host/storage.ts`), but the scenario packages (`Download/*.valkyrie`) and the saves (`*.vSave`) stay on disk until the app reads them, so that a phone does not hold every download in memory. The engine reads files at once, so the app reads them first at its own asynchronous steps: `listingKeptFiles` before a step that lists them (`LoadAllLocalQuests`, `GetSingleQuest`, `GetSaves`; a partial extraction inflates what it takes, so they can go after) and `startingFromKeptFiles` before one that starts a game from them (`Game.StartQuest`, `SaveManager.Load`; they stay read). A new place where the engine reads one needs the same, or it throws `Not read from storage yet`. `GameStateManager.Quest.RestartFromHeroSelection`, which Descent's class selection calls to go back, extracts the package again: it works because the files a game started from stay read. The steps run one after another, and lists read one file at a time (`eachKeptFile`, `listingPackages`), so that a big collection is never in memory at once. Content packs stay in memory, because `GameStateManager.MainMenu` extracts them again every time. Files written during the session stay in memory too: the autosave updates the zip it wrote.
- **Screens**: where the engine opens a screen (`GameStateManager.MainMenu`, `Game.SelectQuest`, `GameStateManager.Quest.Restart`), it calls `game.ui`, and the app runs that screen's ported constructor (`openMainMenu`, `openQuestSelection`, `openQuestDetails`). The app's own words live in `packages/app/src/i18n` (dictionary `uni`: Valkyrie's format, three-letter name, English and Spanish). A Unity class that mixes rules with networking or drawing (`QuestAndContentPackDownload`) keeps its rules in the engine, with tests, and its download and screen in the app.
- **Network**: the engine never sends a request by itself. `HTTPManager.get` goes through `HTTPManager.send`, which `host/boot.ts` sets to the browser's `fetch` (`host/network.ts`); unit tests and the battery leave it null, so whatever asks the store gets Valkyrie's network error (`QuestsManager` goes to `ERROR_DOWNLOAD` and lists the local quests). Never give it a default that reaches the network. Statistics come with the store list (`StatsManager.readListStats`), not from Google Drive. Publishing a game's statistics goes through `HTTPManager.post` (`HTTPManager.upload`), which `host/boot.ts` sets to `postForm`; null in tests, it ends as Valkyrie's network error.
- **Traps**:
  - `Split(sep, n)` keeps the rest of the string in the last part; JS `split(sep, n)` drops it.
  - `Trim(chars)` and `Trim('"')` remove every listed character from both ends.
  - `int.TryParse` and `float.TryParse` leave 0 on failure, and `int.TryParse("1.5")` fails.
  - `Dictionary` iteration follows insertion order: use `Map`, not plain objects, wherever C# iterates.
  - `out` parameters become returned tuples or objects.
  - Overloads become one method that dispatches on its arguments (`perform(op | ops)`), or differently named functions when that reads better; keep the C# name for the most common one.
  - C# throws where JavaScript returns `undefined` or clamps: `s[i]`, `Substring`, `Dictionary.Add`, `dict[key]` and `list[i]`. Use `charAt`, `substring`, `dictAdd`, `dictGet` and `listGet` from `platform/CSharp.ts` wherever Valkyrie's code would throw; some scenarios rely on the crash being a crash (`VarManager.TrimQuest` throws on a variable name shorter than two characters).
  - `float.ToString()` writes up to 7 significant digits (`floatToString`) and `bool.ToString()` writes `True` or `False` (`boolToString`). Round with `Math.fround` after every arithmetic step on a stored float.
  - Enums become `as const` objects plus `type X = number`. Nested classes become module classes exposed as static members, plus `export declare namespace X { type Y = _Y }` for the types (see `QuestData.ts` and `Quest.ts`).
  - Module cycles: `index.ts` exports `Game` first, and code outside the engine imports it only through `index.ts` (tests may also import leaf modules of `platform/`), so `Game.ts` is always the first module to load and can import the classes it creates. While a module loads, only `extends` and static fields may use an imported class, and a class that extends one from another module must not be reachable from that module's imports: otherwise it crashes with a temporal dead zone error. That is why `BoardComponent` (which `ShopInterface` extends) and `LogEntry` (so that `BoardComponent`, `ColorUtil` and `VarManager` log without importing `Quest`) have their own modules.
  - A .NET `Dictionary` throws when it changes while it is enumerated; a `Map` goes on. `EventManager.EventTriggerType` is the known case (a window's quest change is added to the events it walks): since 16 October 2026 it walks a copy instead of throwing, skipping events no longer there and stopping once the quest has changed.
  - `Remove` then `Add` puts a key back in its old slot of a .NET `Dictionary`: use `Map.set` on the existing key, which keeps its place. A new key also takes the slot the last `Remove` freed, so after removals a .NET `Dictionary` is not in insertion order, while a `Map` appends: so far that only changes the order of a save's puzzle sections, but reproduce it wherever the order changes play.
  - A `SortedList` with Valkyrie's `DuplicateKeyComparer` (equal counts as greater) puts a new key before the equal ones already there, because `Array.BinarySearch` compares the stored key with the new one (`QuestsManager.ts`).
  - `String.Replace` is literal, but `replaceAll` reads `$` patterns in the replacement: use `replace` from `platform/CSharp.ts`. Use its `indexOf(s, value, start)` where C# would throw on a start outside the string.
  - When camelCase makes a method and a field collide (`Quest.Undo` and `Quest.undo`), the field gets a suffix (`undoStack`).
  - A `UIElement` made with only a parent keeps the default tag, `dialog`, whatever its window's tag: the log window (`logs`) draws its lines and a developer's variables that way, so while they show every check for a dialog finds one, and `Destroyer.Dialog` removes them (`LogWindow.drawsDialog`, `logLinesShown` in `ui/store.ts`). Look at the tag of a window's parts, not only of its frame.
  - TypeScript keeps a narrowed type across calls that can change the value (`quest.phase` after `activateMonster()`): read it again with a cast.
  - A quest being played has no identifier: `QuestData` builds its `Quest` with `''`, as Valkyrie does, so `currentQuest.qd.quest.identifier` is empty. Name the scenario by its package, `Path.getFileName(currentQuest.originalPath)`, as `EndGameScreen` and the report (`ui/Feedback.tsx`) do.
- **Tests**: `Assert.IsNotNull(x)` becomes `expect(x).not.toBeNullable()`, which also catches `undefined`. NUnit runs inside the Unity editor: where a test depends on it, set `Application.isEditor = true` and put it back afterwards. The app is tested with Playwright (`npm run test:app`, desktop and phone, `*.spec.ts`; run `npx playwright install chromium` once, or set `PW_CHROMIUM_PATH` to another Chromium), and its pure parts with Vitest (`packages/app/tests/*.test.ts`, part of `npm test`). The root `tsconfig.json` compiles those tests without DOM types or JSX, so they import only `.ts` modules that need neither (the board's probe type lives in `board/probe.ts` for that reason, and what is said aloud in `ui/spokenText.ts`, apart from `ui/speech.ts`, which uses the browser's `speechSynthesis`). The service worker exists only in the built app: `pwa.spec.ts` runs on the production build, which `playwright.config.ts` builds and serves with `vite preview` on port 5197, and changes `dist/sw.js` to make a new version (the browser's check for one cannot be routed). A game plays only with its official import, which `screens/ImportGate.tsx` asks for before the investigators or heroes (the game itself opens without one): a test that plays without one opens the app with `?schematic` (development builds only, `schematicMode`), and a test of the import or of the production build imports a made-up one (`tests/fixtures/madeUpImport.ts`: `import.ini`, texts and one-colour DDS or PVR pictures; `importZip` scopes the Import button by the game's `data-section`, because each game has one). Playwright serves Valkyrie's pictures from `referencias/valkyrie` instead of GitHub, and no test reaches the real store: route `raw.githubusercontent.com/NPBruce/valkyrie-store/**` to the clone in `referencias/valkyrie-store` and the packages to `referencias/descargas` (`store.spec.ts`), or abort it (`demo.spec.ts`, which then plays from the local list). Otherwise a run with network sees the store and one without it sees the local list. A routed body goes to the browser in base64 through the DevTools pipe, which closes near 100 MB: serve a big pack light, as `tle.spec.ts` serves TLE (89 MB) with its pictures made blank at their size. To start one of a scenario's events, a test imports the page's own engine by its dev-server address (`/@fs/<root>/packages/engine/src/index.ts`, as `tle.spec.ts` does); the language versions of a scenario are separate packages with their own maps (`Desert_en` and `Desert_es` have different events), so take the names from the package the test opens. A test or an exploration that imports an app module by URL in the page (`import('/src/ui/store.ts')`, as the full Exotic Material test does to read the lock's code) gets the app's own instance only from a dev server that has not hot-updated that module: Playwright starts a fresh one; restart a long-running server after editing.
- **TypeScript and CSS**: `erasableSyntaxOnly` forbids parameter properties and enums; Vitest strips them anyway, so only `npm run typecheck` catches them. Plain CSS files are global: prefix a component's classes (`QuestSelectionScreen.css`'s `.empty` once shrank the save slots).
- **The look**: colours, shadows, radii and fonts are roles in `theme/theme.css`; a component stylesheet never writes a colour (`#…`, `rgb()`…), it uses a role, mixing alpha with `color-mix(in srgb, var(--role) 85%, transparent)`, and `tests/theme.test.ts` fails otherwise, also for a comment that cites an issue as `#1519` (write `issue 1519`). A game's look sets the roles again under `:root[data-game='…']`. Windows wear `.panel`, reading cards `.card`, buttons `.button` (`.button.hud` over the board). Cards are dark, as Valkyrie's `UIElement` (black at 90 %, white text, centred), because authors choose their texts' colours for that: text on a card uses `--card-text` or `--card-quiet`, text on lamplight `--on-accent`, and the schematic board its own `--plan-…` paper and ink. The felt is the board's only: `--table`, set by `:root[data-felt='…']` from Options; the page's colour is `--background`, set apart by `:root[data-theme='…']`. A theme (`themes/themes.ts`, chosen in Options) is more than a colour: Universalis, the default, puts kozka's pictures behind the screens (`themes/Backdrop.tsx`, one per place: the game selection, each game's menu), and will bring each game's frames, buttons and icons; the plain colours keep the screens flat. What a theme draws goes in `themes/`, never into a screen's own code. The app's own options live in `config.ini` under `[Universalis]` (`ui/preferences.ts`), never among Valkyrie's `[UserConfig]` keys. `main.tsx` imports `theme.css` before any component, so a component's rule wins over the theme's at the same specificity; until it did, `.screen` silently overrode the screens' own spacing.
- **Framed buttons** (`border-image`): leave the picture at least one row between the top and bottom slices (`44 52 45` for a 90-pixel button, not `45 52`). With none, a screen or page scaled to 125–175 % rounds the two halves apart, and a 1-pixel slit shows what lies behind; a hover `drop-shadow` glow lit it as a line through the words (3 November 2026, kozka, in all three games). A framed button lights its words on hover (`text-shadow`), never a glow behind it.
- **PixiJS**: curves are tessellated by their size in local units, so a circle of 0.5 board units comes out as a polygon when the camera comes close: the schematic is drawn in hundredths of a unit and scaled down.
  - The board is in perspective: every piece is a `Mesh` with the shader of `board/perspective.ts`, its corners in board units, and one matrix (`camera.ts` `boardToScreenMatrix`) set once a frame. Hit tests go the other way, by the ray of `screenToBoard`, never through Pixi's events.
  - `generateTexture` rounds its frame's width and height down to whole units of the target, so bake a drawing scaled to pixels at resolution 1, or its edges are cut.
  - Pictures that lean away need mipmaps (`autoGenerateMipmaps`, then `updateMipmaps()` for a rendered texture) and `maxAnisotropy`, or the far side shimmers.
  - `Mesh.destroy()` keeps its shader and geometry: destroy them with `destroyQuad` before the textures they hold, or Pixi warns that a texture was destroyed while bound.
  - Drawings over the screens (the game selection's buttons, `screens/gameArt.ts`, and the themes' backdrops, `themes/`) ask for `preference: ['webgl', 'webgpu']`: given nothing better, Pixi 8.22 falls back to a Canvas 2D renderer that skips masks and filters, so the stylesheet's still version is better.
  - Pixi's `Ticker` asks for the next frame only after its listeners return: one that throws (the app's render included) stops the board for good, and the quest's UI pictures, which fade in from transparent every frame, stay invisible while their texts show. `Board.ts` catches its own errors, its frame listeners' too, and a watchdog starts the ticker again after 2 s without a frame (7 November 2026).
  - The board asks for `preference: ['webgl']` only: a single string, as `'webgl'` was until 6 November 2026, lets Pixi fall back to WebGPU and then to Canvas 2D, which cannot run its shader (`board/perspective.ts`). Without WebGL its start fails and `BoardView.tsx` says why on the board (`NO_WEBGL`); `demo.spec.ts` takes WebGL away with an init script to test it.
  - Every drawing (the board, the screens' and the themes') shares Pixi's global pools, so it is made with `newApplication` and destroyed with `destroyApplication` (`board/pixiApps.ts`), never with `new Application()` or `releaseGlobalResources`: those pools go with the last drawing alive. Releasing them destroys the batches a living drawing holds, which it then gives back to the pool, and from then on every drawing on the page crashes in `Batcher.break` (`textures` is null) until it is reloaded: on 17 October 2026 the board, destroyed when a game was left from the investigators' room, did that to the room and then to every backdrop. Each drawing still destroys its filters before its renderer, or Pixi warns that a texture was destroyed while bound.
  - Only a `Sprite` is an alpha mask (a container becomes a stencil of rectangles), and by default it masks with red times alpha, which squares a soft edge: `setMask({ mask, channel: 'alpha' })`. Additive blending inside a masked container works against what that container draws, not against what is behind it.
  - A renderer's `FilterSystem` keeps listening to the last texture a filter or mask drew from, which releasing the shared pool destroys, and Pixi then warns: destroy `renderer.filter._globalFilterBindGroup` first, then the app, then your textures. A drawing that React destroys before it started (StrictMode mounts twice in development) still goes through `destroyApplication`, which counts it out.
- **Pictures**: `host/pictureFiles.ts` reads them for the board and the screens alike: PNG and JPEG through the browser, DDS through `host/dds.ts` and PVR (ETC2, from Android imports) through `host/pvr.ts`, both with their rows from the bottom (Unity's order, which Valkyrie's importer keeps), and Valkyrie's own fetched from its repository. `tests/pvr.test.ts` compares random blocks of every ETC2 mode with a reference decoder (`tests/fixtures/make-etc2.py`); an ETC2 bit read wrong changes few pixels, so keep that comparison.
- **The official import** has its own store in the origin private file system (`import/<game>/` and `import/<game>.json`, `host/officialImport.ts`), too big to load whole at start: storage.ts's mirror leaves the import folders alone. The engine sees the files through a virtual tree (a DDS or PVR by its stored header, so `FileToTexture` gets the real size and format) plus the texts it reads at once, kept in memory (`importSource.isReadAtOnce`). The app reads the rest from the store: pictures through `host/pictureWorker.ts` (decoded and halved to 2048 or, on touch screens, 1024 pixels, so an atlas part must scale with the decoded size), sounds through `importedFile`. A worker module must not export values the page imports, or importing them runs the worker's code in the page: shared types and constants live in `importSource.ts`.
- **Dev server**: restart it by its own command line (`node …/vite --port 5200`), never with a pattern `pkill` also finds in the shell that runs it: that kills the shell. In development the page sends its warnings, errors and the import's picture traces to `packages/app/dev.log` (`host/devLog.ts`, plugin in `vite.config.ts`): when something fails only in the user's browser, have them reproduce it and read that file on their PC.

## Order
1. Foundations with their tests: `IniRead`, `DictionaryI18n`, `StringKey`, `LocalizationRead`, the virtual file system, and `.valkyrie` and `content_pack.ini` loading.
2. Battery v1 (below).
3. `QuestData` (QuestComponentTests), then `EventManager`, `VarManager`, `VarTests` and their tests, including `StartQuestEvent`, `Quest.ChangeQuest` and `VarManager.TrimQuest`, which the TLE scenarios need right after their intro.

## Editor
- The editor writes exactly what Valkyrie's editor writes (`QuestEditor.Save`: header, sections, blank lines, the order of components and of texts, `DictionaryI18n.SerializeMultiple`), so that a quest saved by one opens the same in the other. The order of a .NET `Dictionary` after removals matters there: components and texts go through `netSet`, `netAdd` and `netRemove` (`platform/NetDictionary.ts`).
- Where Valkyrie's editor would break a quest, Universalis does the safe thing, marks it `Not in Valkyrie` and tests it: a rename skips a name whose texts were left in the localization, keeps a trigger that only starts with `Defeated` and the old name, and carries `{c:…}` and `{qst:….}` in the texts and a custom monster's attack texts (built from its name when the quest loads, as an event's button labels are) along.
- A save never loses a scenario (`Not in Valkyrie`): `QuestEditor.save` first keeps, as a version, the files it will replace and those the quest.ini on disk lists (`QuestEditorVersions`: a zip in `<game>/EditorVersions/<scenario>/<time>.zip`, the newest 20, none when nothing would change), then reads what it wrote back as Reload would and builds the files again from it (`readBack`); when they differ (`lastSaveUnstable`), it puts the old files back and the editor keeps what it holds. Deleting a scenario forgets its versions. Code that saves (the app, the round trip, a package) checks `lastSaveProblems` and `lastSaveUnstable`, never only the first. Beside the versions, the app keeps a draft of what is not saved a moment after each change (`QuestEditorVersions.keepDraft`, from `editor/session.ts`), offered when the scenario opens again after the editor closed without saving; saving, Reload, restoring a version and leaving on purpose throw it away.
- `npm run roundtrip` opens, saves and opens again every downloaded quest, and `-- --edit` renames, undoes, redoes and deletes in each of them: both must end with nothing `changed`, no `error` and no edit problems (about a quarter of an hour; with `--edit`, about forty minutes, most of them in a few Mansions packages of a hundred quests or more, such as *Pruebas*, *Snow* and *Desert*). Valkyrie's own float rounding (`rounded`) and the quests its editor cannot open (`cannot-open`, such as a missing TileSide) are not failures.
- The editor's screens are only in development builds (`import.meta.env.DEV`), until kozka says it is ready: `App.tsx` loads `editor/EditorScreen.tsx` with `lazy` behind that flag and the main menu shows its entry only then, so a production build has none of the app's editor code, styles or texts (`pwa.spec.ts` checks the built files). The engine's editor rules do reach it, dormant: play code that test mode uses refers to them (`GameStateManager.Editor` from `ClassSelectionScreen` and `GameMenu`). For a few days from 12 November 2026 it is open to try in the published app too: `EDITOR_PREVIEW` in `packages/app/editorPreview.ts` (`false` puts everything back). While it is on, the menu's entry opens a large warning first, in development too (`ui/EditorWarning.tsx`), which lets in only a computer (`(hover: hover) and (pointer: fine)`; Playwright's phone has neither, so the editor's specs skip there and `editor-preview.spec.ts` checks the refusal), and the specs go past it with `pressEditor` (`tests/fixtures/editor.ts`). The app reads the switch only as `__EDITOR_PREVIEW__`, which `vite.config.ts` writes in: Rolldown does not fold a constant imported from another module, so `import.meta.env.DEV || EDITOR_PREVIEW` imported kept the editor's chunk in the build with `false` (12 November 2026). Check the switch both ways by building.
- The text mode (`QuestEditor/ComponentText.ts`, `editor/TextMode.tsx`) shows a component's section, or the quest's own, and its texts in one language as Save writes them, and applies an edit by loading the whole quest again from files that hold those lines (`QuestEditorHistory.loadFiles`), as Reload would, so that the editor then holds what Valkyrie would read. It refuses another section, another component's texts and a change of the quest's format or game (Save writes them itself), and puts the quest back when Valkyrie would stop drawing the result (a TileSide that is not there). A component is a new object after it: look it up again by name.
- The workbench (`editor/Workbench.tsx`) changes a quest only through `session.ts`: `change(label, action)` records the history first (Undo's tooltip is the label) and checks the quest again afterwards, and `select(name)` selects as `QuestEditorData.SelectComponent` does, draws the editor again and, unless the map chose it, moves the camera to it as Valkyrie's panels do (`SetCamera`). Calling the engine directly leaves the screen stale or the change out of the history.
- The event panel (`editor/EventPanel.tsx`) only draws and picks: what each field does to the quest is the engine's (`QuestEditor/EditorComponentEvent.ts`, `EditorComponentVarTestsUtil.ts`), ported from the functions of Valkyrie's panel and of its button window, so that a field behaves as there (a dialog typed shows the event and gives it a first button, `{NEW:Event}` makes and names the event as Valkyrie does, a typed variable is cleaned as `NewVar` cleans it, a button's failed action goes when its condition does). Which parts a token, door, UI element, spawn or puzzle shows follows their panels' overrides (`parts()`). A browser test of a field checks the lines text mode shows, which are what Save writes, not only the form.
- The selection windows (`editor/Chooser.tsx`) take their items and their filter from the engine (`QuestEditor/SelectionTraits.ts`, Valkyrie's `UIWindowSelectionListTraits`): open one as the panel opens Valkyrie's (`excludeExpansions`, which keeps the game's own base pack that Valkyrie's check leaves out, then the source of what is chosen picked, `SelectionTraits.sourceOf`), with the items taken when it opens, and leave the workbench's keys alone while it is open (R would turn the piece behind it). Valkyrie's `{NONE}` items have no source, so its window never shows them: leave them out where picking one would write a broken component (a token's type, a tile's picture), and offer none where it writes something valid (the quest's cover, a UI element's picture, which makes it a text, an item's inspect event). Picture paths are written with forward slashes, where Valkyrie on Windows writes backslashes that only Windows finds.
- The editor's map (`editor/EditorMap.tsx`) is the game's board seen from above (tilt 0, the player's lean put back afterwards), with a grid drawn by `editor/EditorBoard.ts`, a subclass, so that the built app has none of it. Whatever the tilt, the middle of the board shows what Valkyrie's 10° camera shows there, so the camera's point is not the middle of the map: a test finds a board point with `universalisBoard.pointOnPage` (the map sets the probe too), never from the map's size. At each change the workbench draws on the map what Valkyrie's panels draw (`EditorComponent.drawOnMap`: `Clean`, the selected piece solid, its place marked with the target, tagged `editor`); a mark is a picture on the token canvas, so the map's presses look past what belongs to no component (`componentAt`), or a door under its mark could not be pressed or dragged (`universalisBoard.tokenObjects` lists the marks).
- The workbench's layout (`editor/Workbench.tsx`, `editor/layout.ts`, 24 October 2026): the component's panel on the left as in Valkyrie, the list on the right, the panel below; each folds and is sized by dragging its edge, kept per device in `localStorage` (a convenience: it starts from the defaults when storage is blocked). The panes' grid has five columns (panel, handle, map, handle, list): a folded side leaves an empty `<span>` where its handle was, or the map falls into the handle's column. Pixi's `resizeTo` follows only the window's size, so the editor's board watches its box (`ResizeObserver` in `EditorBoard`); a new board inside a resizable box needs the same. What the bar does not show is in its File menu (`role="menu"`, entries `menuitem`): a test opens it first (`fileMenu` in `editor.spec.ts`). A tool button's name is its words and its tooltip adds its keys, except Undo and Redo, whose tooltip is what they take back (the tests read it). The chrome uses `--font-tool`; the scenario's own texts (the dialog, its preview) keep `--font`. Its panes never get shorter than the map's 12rem, or the map, which is positioned, draws over the panel below, and a click there lands on its canvas (the taller panel did it on an 800-pixel screen); the panel's tabs scroll sideways instead of widening the page on a phone, and do not shrink, as a scroll box in a column of flex boxes would. A row of the editor's list stacks its tools under its name on a phone (40rem): with three tools, the grid's `auto` column left the name one letter wide, and Playwright could not press it.
- The graph (`editor/graph/`, 26 October 2026): `model.ts` builds it from the quest's components at every redraw (not from `session.graph`, which the checks rebuild 300 ms later) and lays it out as a tree per row, a component opened only the first time and later drawn as a copy, so `buildGraph` stays linear; its unit test (`tests/graphModel.test.ts`) builds a quest with a stand-in `Game.game` (`currentLang`, a real `MoMGameType`, `questsList`). `GraphPanel.tsx` pans and zooms by writing the transform straight to the DOM and redraws once a frame, drawing only what is near the view and, below 22 % zoom, only the shapes, so that *Bruma Maldita 2* (850 events) still moves smoothly. Port positions come from `layoutOf`, which must agree with the heights the node's parts are drawn at (`SIZES`), set inline. A change made there goes through `change()` like any panel's (Undo's tooltip names it) and selects what it made. The graph's keys stop at it (React's `stopPropagation` keeps them from the workbench's window listener). Its browser tests skip the phone, where the view shows a corner of the graph. Choosing its tab makes the panel below half the window: at 190 px its toolbar did not fit, the tab body (which hides what does not fit) was scrolled by Playwright to reach a node, and the fitted zoom fell to shapes only, with no ports to press.
- The screen of UI elements (`editor/UIStage.tsx`) lays them out with `board/questUI.ts`, as the game does, and turns a drag back into Valkyrie's units: a pixel is `1 / screen.width` (or `screen.height` with vertical units), negated for an element aligned right or bottom; places and sizes are rounded to hundredths, as an author types them. It draws them in the order the shown event adds them, as the game does (the later on top); the chosen one's frame, name and handles go in a layer above them all (a portal), never by raising the element itself, which put a background over its text (26 October 2026).
- A scenario's long texts and buttons' labels are typed in `editor/RichField.tsx`, a `contentEditable` box that draws Unity's rich text as it is typed. The text is parsed with `RICH_TAG` and built node by node: an author's text never goes through `innerHTML`. It is written back only when it was typed in (`dirty`), so that loosely written tags are never rewritten by a look. DOM ranges are live: a caret kept across a refill falls to the start of the box, so it is dropped then. Playwright's `fill` works on the box, but its content is read with `toHaveText`, not `toHaveValue`. The symbols' row is only for the texts a game shows (`symbols={false}` for the scenario's description, synopsis and authors).
- A press on the map takes tokens before doors and doors before tiles (a door's picture covers the token beside it), and a press on the piece already chosen takes the next one under it, round and round; the status line lists them all. A browser test that presses a piece already chosen gets the one under it.
- The panel shows no numbers for a piece's place, which the map sets (a drag; an event or a monster place with "Colocar en el mapa"); the tests read it from `.editor-piece`'s `data-x` and `data-y`.
- The panel's flat view (`layout.flat`, the button beside text mode) shows a `Fold` given `part` without its heading and never folded; give `part` only to a component's own parts, not to the problems or the links around them. A menu of the bar measures itself when it opens and opens towards the left if it would leave the screen (`editor-menu-end`). A right click on the map offers to make a piece where it was clicked (`MapMenu` in `EditorMap.tsx`), snapped as a drag would be.
- The editor's own colours (`data-editor-theme` on `.editor-workbench`, `layout.ts`) set the theme's roles again under that attribute in `theme.css`; nothing else in the app changes. The game's dark card stays under the texts in every one, as their authors chose their colours for it.
- The bottom panels read the quest's graph as the checks left it (`currentSession().graph`, `QuestGraph`): the tree of events (`editor/EventTree.tsx`) and the variables (`editor/VariablesPanel.tsx`). The tree opens a branch only when asked and never a component already on its way, or a scenario of hundreds of events would draw thousands of rows.
- The texts' table (`editor/TextsPanel.tsx`) and the book (`editor/BookPanel.tsx`) read the texts as the dictionary holds them now (`textsNow()` in `session.ts`, `DictionaryI18n.allEntries` once a redraw), not as the last check saw them, or a cell just written would show its old text for a moment; and they draw a page at a time (200 rows, 150 passages), because *Eyes Behind the Mirror* has 3,546 texts in 7 languages and drawing them all took seconds at every change. A text of the scenario written in one language goes through `QuestEditorTexts` (`addEntry` or `removeEntry` with the language); Valkyrie's panels write the current language and take an emptied text from every language, which the fields keep.
- The language the fields write in is the app's, as in Valkyrie (`LocalizationRead`'s current language); the editor changes it as the options do (`editor/language.ts`, `selectLang`). An editable dictionary must keep its data when a language it lacks becomes required: Valkyrie's `AddRequiredLanguage` empties it, which threw away every text not saved when the language changed with the editor open (Valkyrie never meets it, as its options are reached only by leaving the editor); `tests/QuestEditorTests.test.ts` checks it.
- A test from the editor (`editor/test.ts`, Valkyrie's Save & Test) plays on the game's screens, which reach the editor only through `ui/editorTest.ts`: the editor sets it while a test runs, so the built app, which has no editor, never draws the test panel or the menu's Editor button. While one is set, `ReactUI.mainMenuScreen` goes back to the editor instead, once what ended the game has finished (`setTimeout`): Valkyrie's `EndEvent` goes to the main menu for a scenario that is not a package. The engine's own ways back (`GameMenu.Editor`, Descent's `ClassSelectionScreen.BackButtonAction`) reach the app through `QuestEditor.begin`, which draws the editor's screen with `game.ui.questEditorScreen` (Valkyrie's `MenuButton` and `ToolsButton`): while a test is set, that opens the editor again with the scenario's history; a new way back needs nothing more. The panel starts closed on a phone, where it covers the game's windows (and Playwright's clicks land on it). `EventManager` keeps why each event started only in test mode (`started`); a caller that queues events for a reason the panel should name wraps its `queueEvent` in `queueBecause`. Its button, «Guardar y Probar», made the tests' `getByRole('button', { name: 'Guardar' })` find two buttons, as Playwright matches a part of the name: they press Save with `exact: true`.
- Valkyrie's editor lists every quest below its user folder, hidden ones too (`QuestLoader.GetUserUnpackedQuests` walks `ExtractManager.DirList`, which is recursive): a campaign's adventures are scenarios of its list, each opened, saved and packaged alone. Read that listing before assuming what Valkyrie's editor can open (E.9 first took it to open only a campaign's own quest). Universalis shows them under their campaign (`editor/campaign.ts`: the campaign is the outermost folder above with a quest.ini) and works on an adventure as part of it: its checks are the whole campaign's (`session.root`), its package and export are the campaign's, a test of it changes quest from the campaign's folder (`ToolsButton.startTest(…, { root })`: Valkyrie's looks for the next adventure inside the adventure and misses it), and a button's next events offer the campaign's other quests. `EventManager.started` survives `Quest.ChangeQuest`, which makes a new EventManager, so the test panel follows a whole campaign.
- Under DooM's button the editor is DooM's, as its quest list is (`screens/doom.ts`): it lists the campaigns whose own quest asks for DooM, a new one gets `packs=DooM`, and a test chooses among the marines (`heroesToChoose`, shared with the hero selection). The test panel waits while the heroes and their classes are chosen: open beside Descent's class selection, it covered the second hero's column.
- A long text of a panel is `TypedText` with `multiline`, which Valkyrie draws as `UIElementEditablePaneled`: it brings the row of the game's symbols over the box (each puts its code where the caret was). Use it exactly where Valkyrie's panel has a paneled box; a one-line box (a name, a short author, a button's label, Mansions' unable button) has none.
- The editor's own texts are a dictionary of their own, `edi` (`editor/i18n`, loaded by `editor/text.ts`), in English and Spanish while it is not ready (the other languages read the English ones, also while it is open to try); the other eleven languages come before it is ready. Look a new key up first: one given twice is read once, with its first text, and `editorTexts.test.ts` fails on it (the text mode's `EDITOR_TEXT_STEP` nearly took the table's). Valkyrie's editor's words are its `val` keys (`SCENARIO_FOLDER_NAME`, `CREATE_PACKAGE`…), already in every language.
- The checks (`QuestEditor/checks/`) are not ported, because Valkyrie's Validate does nothing: each comes from a rule of the skills' validators, checked against Valkyrie's C# before it is written (`TokenBoard` for a spawn's placements, `LocalizationRead.DictLookup` for texts). `node tools/battery/checks-compare.ts` compares them with those validators on the 228 scenarios of the store (`--code <code>` shows both sides of one); a difference is a bug of ours, a validator's mistake, mended in the skill (in both copies, the plugin's and `herramientas/`, with the plugin's version raised, as on 24 October 2026), or goes into `EXPLAINED` with its reason. It keeps the validators' findings in `tests/battery/checks-python/`: delete that folder after changing a validator. A level says what Valkyrie does: `breaks` when it closes or stops an event, `wrong` when the player sees something other than the author meant, `hint` otherwise. A new code needs its text in English and Spanish (`PROBLEM_<CODE>` in `editor/i18n`, the problem's params by name, `{target}`, as `editor/problemText.ts` fills them): `packages/app/tests/editorTexts.test.ts` takes every kebab-case string of the checks' sources as a code and fails on one without a text. The app's unit tests cannot import `editor/text.ts` (Vite's `import.meta.glob`, `document`): what they need of the editor's texts goes through `editor/edi.ts`. A problem gets a button that mends it (`QuestEditor/ProblemFixes.ts`) only where the mend is certain and writes what Valkyrie reads, and `fixOf` gives none once it is mended, so that a second press does nothing; what the author asked not to be told about again is kept beside the versions (`QuestEditorVersions.ignored`, by `problemSignature`, params included so that a changed problem comes back), never in the scenario's files, and a problem that breaks Valkyrie cannot be left untold.
- The analysis (`editor/analysis/`, 8 November 2026) plays a Mansions scenario with its own variables and its own map (`mapModel.ts`, ValkyrieMCP's spaces placed as `Quest.Tile` places the picture), never through the engine's `Game`, `VarManager` or `EventManager`, which hold the scenario being edited (`VarManager` also logs into `currentQuest`, null in the editor). What it reads of an event must follow Valkyrie's order (`EventManager.TriggerEvent`: tests, operations, add, remove, the window, a button's operations, then the next events, the first that passes or one at random); a new rule of play goes into `simulate.ts` with that order kept, and its figures are a guide, so its texts say so. It is seeded (`analyze.ts`), so the same scenario gives the same figures.
- One `$end` event often closes both a victory and a defeat (`Event_gracias_jugar` in La bruma maldita 1): the analysis counts an ending by the event that led to it (`endVia`), never by the end event alone. When the simulated table gets stuck, look first at what it chose, not at the rules: a dialogue hub whose new branch lies a few events behind one already heard, a cumulative test left half done, or a token whose way on reads a variable deep in its conversation. `blockers.ts` names where the way to an ending stopped; run it on the failing game before changing `simulate.ts`. A scenario's texts are readable only in the languages its dictionary has loaded: `Game.currentQuest` adds the quest's own, so a test that loads a `QuestData` alone reads none of a Spanish-only scenario's texts in English; `analyze` asks for the language itself. The analysis is calibrated against the store's figures (`docs/analisis-calibracion.md`: `tools/analysis-calibration-data.mjs`, then `CALIB=<folder> npx vitest run analysis-calibration`): run it before and after a change to `simulate.ts`, and judge a change by the 127 scenarios, never by one. Valkyrie's `Defeated` triggers carry the monster's kind (`DefeatedMonsterCultist`, a custom monster's name) or its spawn's name; the minutes shown are `estimateMinutes`, fitted on that data, because the simulated minutes alone predict a real table's poorly. Besides playing, `investigation.ts` reads the scenario as the skill's `investigacion.md` asks (rooms placed with tokens and no words about them, tokens that change nothing, variables nobody reads): a silent event that places a room is said by the window that led to it. `quota=<variable>` both reads and writes the variable (`DialogWindow.onQuota`).
- Valkyrie reads texts in ways that look like slips: `DictLookup` looks for a lookup's end from its second character on and throws when the text ends first (a `{qst:` never closed, which some translations have), `DictQuery` takes the key up to the first `:` outside brackets when the lookup holds brackets, and `ReplaceComponentText`'s `.` stops at a line break, so a `{c:…}` split by one is shown as it is. Content that two packs define keeps the first definition and both packs' sets (`ContentData.AddContent`): `TileSideCampsite` has the conversion kit's back, not Path of the Serpent's. `FindLocalisedMultimediaFile` tries `<quest>/<language>/<name>` first, and the path is normalized before the file is looked for, so a main quest's `../Sounds/x.ogg` reaches its own `Sounds` through any language's folder (*Gift for a King*); in the editor (`editMode`) it looks only in the quest's folder, so the checks look as a player does.

## Battery
- **v1** loads every quest; **v2** starts every quest the list shows and plays a few steps. Both run in `npm run battery`.
- **Inputs**:
  - Valkyrie's 62 built-in packs from `referencias/valkyrie` at the pinned commit.
  - The community packs and every scenario package in `referencias/descargas/` (`node referencias/descargar-escenarios.mjs`).
  - Optionally, extra folders such as `valkyrie-questdata` or the user's own scenarios.
- **Unit**: every `quest.ini` in every package, not just the root one (2,133 in MoM and 295 in Descent today).
- **Result per quest**:
  - `ok`.
  - `warnings`, with their kinds: missing media, letter case, `\`, mixed line endings, duplicate keys…
  - `fatal`, for a `ValkyrieFatalError`.
  - `crash`, for any other exception.
  - `missing-packs`, when a pack it requires is not available.
  - `invalid`, for a main quest that Valkyrie would not list: unknown format, another game, no type, or hidden.
- **Baseline**: `tests/battery/baseline.json` is committed. `npm run battery` fails if any quest gets worse than its baseline. Improvements update the baseline in the same commit.
- **Report**: `tests/battery/report.json`, not committed, plus a one-screen summary printed to the console.
- **How it runs** (`tools/battery/`): `environment.ts` sets up a virtual file system with the base data (empty stand-ins for its images), the import folder (any `.dds` or `.ogg` counts as present), the community packs in `Download/ContentPacks`, and a `Game` with every pack loaded, following `GameSelectionScreen`, `GameStateManager.MainMenu` and `Game.SelectQuest`. `battery.ts` puts each package in `Download`, extracts it as `Game.StartQuest` does and loads each `quest.ini` the way Valkyrie reaches it: a quest that the list would show (valid, of this game, not hidden) through `QuestData.Quest` and `new QuestData(q)`, with its missing packs; any other `quest.ini` below the root as `Quest.ChangeQuest` loads it, with `new QuestData(path)` and no checks. `checks.ts` repeats the lookups Valkyrie makes while playing (pictures and sounds by pack name, then in the quest folder; TileSides; tokens; `add=` targets) and reads what `IniRead` and `DictionaryI18n` log.
- **v2** (`tools/battery/start.ts`), for each quest of the list that loads: `GameStateManager.Quest.Start`, two heroes (or the quest's minimum), `Game.EndSelection`, the first free class of each hero in Descent or the starting items in Mansions, `Game.QuestStartEvent`, then ten choices, always the first (the first button a dialog lets press, else the topmost clickable element of the quest's UI). It records `ok`, `not-started`, `fatal` or `crash`, what waits for the player, a change of quest on the way, and the warnings Valkyrie writes (missing events, items or monsters it cannot choose, bad colours…). The baseline keeps `start` and `startWarnings` for those quests. Pictures that are not here are stand-in headers, so that `FileToTexture` gets a size: Valkyrie's own with their real size (`manifest.json` records it), the official import's of 4096×4096.
- **Options**: `--game MoM|D2E`, `--filter <text>`, `--extra <folder with .valkyrie files>` and `--update-baseline`. Updating keeps the entries this run did not cover (another game, a filter, a package missing on this machine), and writes one quest per line so that a diff shows exactly what changed. A full run takes about two minutes.
